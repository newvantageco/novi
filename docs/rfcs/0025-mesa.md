# RFC 0025 — Mesa, and a renderer chosen by measurement

**Status:** Implemented
**Depends on:** RFC 0001 (desktop), RFC 0007 (base/desktop split), RFC 0015 (native toolchain)

> **Summary.** Mesa 24.2.8 — EGL, GLESv2 and GBM, with the softpipe and
> virgl gallium drivers and no LLVM — is built in the library stage,
> and wlroots is built with its `gles2` renderer and `gbm` allocator on
> top of it. Both renderers ship. The default stays `pixman`, because
> that is what measured faster on every machine this project can run
> on, and the choice is now a declared key rather than a hardcoded
> line in an init script.

## Motivation & Problem Statement

There was no GL stack. Not a slow one — none. `novi-shell` rendered
through wlroots' pixman software renderer, wlroots was configured
`-Drenderers=[] -Dallocators=[]` on purpose, and no program that wanted
OpenGL could run on this system even in principle. `libwayland-egl` was
in the image with no consumer, which RFC 0007 notes as one of the four
libraries nothing NEEDs.

That is the gate in front of a stated goal of this project. Games want
GL. So does anything that draws with a GPU. And on a laptop with a real
driver, compositing in software is the difference between a desktop
that feels immediate and one that does not.

## Decisions

### 1. softpipe and virgl. Not radeonsi, not llvmpipe, not yet iris.

`-Dgallium-drivers=softpipe,virgl -Dllvm=disabled`.

- **softpipe** is pure software rasterisation and needs no LLVM. It is
  the only driver guaranteed to work in a plain QEMU with no host GL,
  which makes it the one the whole pipeline can be *verified* on rather
  than reasoned about.
- **virgl** is the accelerated path inside a VM: QEMU's `virtio-gpu-gl`
  passes GL through to the host. Small, and no LLVM either.

**radeonsi and llvmpipe both need LLVM**, which is an enormous
cross-build of its own and a separate piece of work. Intel's **iris**
needs no LLVM and is the obvious next driver — it is deliberately
absent rather than shipped untested, because QEMU emulates no Intel GPU
and this project has never run on physical hardware. Same call as the
panel's absent battery indicator.

### 2. EGL and GLESv2 only. This is not yet a gaming stack.

`-Dglx=disabled -Dglvnd=disabled` costs desktop `libGL`. What ships is
EGL + GLESv2, which is exactly what wlroots' `gles2` renderer wants and
is **not** enough for most existing OpenGL games, which want full GL
through libglvnd. Worth stating plainly rather than letting the word
"Mesa" imply more than was built.

**A correction, from actually asking.** `novi-glinfo` reports
`EGL client APIs: OpenGL OpenGL_ES` — so desktop OpenGL *is* available
through EGL, and a program that calls `eglBindAPI(EGL_OPENGL_API)` can
have a desktop GL context today. What is missing is not the capability
but the `libGL.so.1` an existing program expects to link against and
call through. That distinction matters for what item 3 of the roadmap
below is actually for: libglvnd supplies the entry points, not the
ability.

### 3. Mesa lives in the library stage, and so does zlib now.

Mesa has to exist before wlroots, because wlroots links it. Both are
linked by more than one thing. So Mesa is section 13 of
`06-wayland.sh`, between libdrm and wlroots.

That dragged **zlib** with it: `libgallium`'s `DT_NEEDED` names
`libz.so.1`, and zlib was built at stage 21. A library built after its
consumer is invisible in a warm tree and fatal in a clean one — the
novi-launcher/fcft bug and the novi-panel/libnl bug, for a third time.
zlib moved to section 12; `21-imagelibs.sh` now checks for it and fails
loudly rather than silently linking whatever it finds.

### 4. The C++ runtime is its own package, taken away from the compiler.

Mesa is the first thing in this image with any C++ in it, so
`libgallium` names `libstdc++.so.6` and `libgcc_s.so.1` and **nothing
shipped them**. They existed only in the cross toolchain, in `lib64`,
which musl's loader never searches — RFC 0015 records the identical
trap for the native toolchain, where C worked perfectly and C++ died at
exec.

RFC 0015's `gcc` package was already shipping those exact paths, so
claiming them for Mesa without further change would have given one path
two owners. The runtime is now its own `gcc-libs` package; `gcc` drops
it and depends on it. That is what every distribution does, for the
reason on display here: far more things need to *run* C++ than to
compile it.

### 5. Both renderers ship, and the default is measured, not assumed.

wlroots picks a renderer at runtime, so building `gles2` does not
remove `pixman` — it is mandatory and always present. That is what made
it possible to compare them instead of switching on faith.

wlroots' own auto-detection picks `gles2` whenever the DRM backend
reports a render node; reading `render/wlr_renderer.c`, the pixman
branch is gated on `!has_render_node(backend)`. The heuristic assumes a
render node means hardware acceleration. **It does not**: `virtio_gpu`
offers `/dev/dri/renderD128` in a plain QEMU with no host GL, and what
answers there is softpipe.

Measured on a booted machine, identical load (a terminal flooding
output for 20 seconds), `novi-shell`'s own CPU time:

| renderer | CPU ticks / 20s |
|---|---|
| pixman | 363 |
| gles2 (softpipe) | 1998 |

**5.5× more**, which is unsurprising once stated: software
rasterisation *through a GL API* is strictly more work than pixman
drawing 2D directly. Auto-detection gets this exactly backwards on
every machine this project can currently test on.

On real hardware the answer inverts, and by a much larger factor.
Nobody here can measure that. So the default is the one that was
measured, and it is a **key** rather than a hardcoded guess:

```
display.renderer = pixman        # pixman | gles2 | auto
```

Read by `init/services/novi-shell/run` when the compositor starts. It
is a read-at-use-time key like `power.blank` and `storage.automount`:
nothing holds it, it cannot drift, `apply` has nothing to converge, and
therefore `converge_key` never runs to reject a typo — so the
**observer** validates it, and an unusable value reports as drift,
which is where a person finds out. It is the one read-at-use-time key
whose "use" is a process launch, so a change takes effect at the next
start of the desktop rather than immediately.

## What was verified

On a booted image, not compiled and assumed:

- The full pipeline initialises: `Creating GLES2 renderer`, `Using
  OpenGL ES 3.1 Mesa 24.2.8`, `GL vendor: Mesa`, `GL renderer:
  softpipe`, shaders compiling, `Created GBM allocator with backend
  drm`, `Using DRM node /dev/dri/card0`, `Allocated 1920x1080 GBM
  buffer`, `Created GL FBO`. EGL → GLESv2 → softpipe → GBM → DRM, end
  to end.
- The desktop renders through it — screenshotted, panel and background
  drawing normally.
- The measurement above, both renderers, same load.
- `novi-state set display.renderer gles2` then a restart switches the
  compositor to the GL renderer; back to `pixman` switches it back.
- `display.renderer = vulkan` reports as drift
  (`unsupported (actual)` against `vulkan (declared)`), and restoring a
  valid value converges.
- pkgsplit derives `mesa`'s dependencies correctly from the ELF graph:
  `expat,gcc-libs,libdrm,wayland,zlib`.

## Consequences

- **~18 MB** on the desktop: 15.4 MB of Mesa (nearly all of it the one
  `libgallium` megadriver, down from 75 MB unstripped) plus 2.6 MB of
  GCC runtime. Packages, never base — the base image stays
  console-only, per RFC 0007.
- **`libgallium` is invisible to the dependency graph.** libEGL loads
  it by name at runtime, so nothing NEEDs it and `closure()` cannot
  reach it. It is claimed by `PACKAGE_TABLE` instead — the same dlopen
  blind spot as `libdrm_amdgpu`/`nouveau`/`radeon`, and the reason that
  table exists alongside the graph.
- **A new build-host dependency**: Mesa's build needs the Python `mako`
  template engine. Checked up front with a message that says so, the
  same reason `05-kernel.sh` checks for `depmod` rather than letting
  `modules_install` warn and continue.
- **The meson cross file now sets `needs_exe_wrapper = true`.** Without
  it meson auto-detects, concludes it can run target binaries directly
  — this host has `/lib/ld-musl-x86_64.so.1` symlinked at the sysroot's
  libc, so it genuinely can — and then runs them *without* the
  wrapper's `LD_LIBRARY_PATH`, which is where the toolchain's lib64
  runtime is named. A C++ target binary died on "Error loading shared
  library libstdc++.so.6" while `g++` was working perfectly, and meson
  reported it as "Executables created by cpp compiler ... are not
  runnable". Exporting `LD_LIBRARY_PATH` globally was rejected: it
  would apply to the host's own glibc-linked meson, ninja and python.

## Addendum: a client, and what it did and did not prove

This RFC originally verified the COMPOSITOR and nothing else.
`novi-glinfo` (build/37) is the client half, and it exists for two
reasons: EGL's Wayland platform and buffer sharing back to the
compositor is a completely different path from the compositor's own
GBM/DRM one, and it is the path everything except novi-shell will
take; and it is the tool a person needs the moment they act on
`display.renderer`, because "softpipe" and "iris" look identical from
outside and the difference is the whole reason the key exists.

Verified on a booted machine: a GL client gets `OpenGL ES 3.1 Mesa
24.2.8` on `softpipe` through the Wayland platform, opens a window,
and renders — screenshotted, teal, with the compositor's own title bar
and control dots around it. **The first GL program to run on this
operating system.**

**It renders identically under `pixman` and under `gles2`, and the
reason is the thing to carry forward, not the result.** A compositor
needs a GL renderer to import a client's *GPU* buffers — so the
obvious worry was that this RFC's measured-best default, `pixman`,
would make GL applications impossible. It does not, here: softpipe has
no GPU, so Mesa renders into shared memory and hands over an ordinary
`wl_shm` buffer, which any renderer can composite. No dmabuf traffic
appears in the compositor's log under either setting.

So the pixman default is safe **on every machine this project can
currently test**, and that is exactly as far as it goes. On real
hardware a client would produce GPU buffers and need dmabuf import,
which pixman cannot do — so `display.renderer = pixman` on a machine
with a working driver should be expected to cost GL clients, not just
compositor performance. That is a reasoned expectation from the
mechanism, not a measurement, and it is the second thing to re-check
on metal.

## Roadmap

1. **iris**, for Intel hardware. No LLVM, and the single largest
   real-world win available — but unverifiable here.
2. **LLVM**, and with it llvmpipe and radeonsi. Large.
3. **libglvnd and desktop libGL**, without which most existing OpenGL
   software cannot run at all.
4. **Re-measure on metal**, and re-run `novi-glinfo` there. Every
   number in this document is from software rasterisation in a VM. The
   default is `pixman` *because* of that, and on a machine with a
   working driver it is the wrong default twice over — slower, and
   (per the addendum above) probably unable to show a GL client's
   buffers at all. Which is exactly why it is a key.

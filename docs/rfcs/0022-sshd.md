# RFC 0022 — sshd, and the port that does not open itself

**Status:** Implemented
**Depends on:** RFC 0005 (users), RFC 0016 (firewall), RFC 0019 (ssh)

> **Summary.** `pkg install openssh-server` puts a daemon on the
> machine. `services.sshd = on` runs it. `network.firewall.allow = 22`
> lets the world reach it. Those are **three** separate acts, on
> purpose. The host key is generated on first start and exists nowhere
> in the image; root cannot log in over ssh at all.

## Motivation & Problem Statement

RFC 0019 shipped the ssh client and said, in the package's own README,
exactly why the daemon was not in it: *"a listening service needs host
keys, a privilege-separation user, an s6 service, a declared state key
and a hole in the firewall. Each of those deserves a deliberate
decision."* This is those five decisions.

The gap it closes is the largest remaining one for a machine with no
monitor. Novi installs, boots, gets a lease and joins a WiFi network —
and then the only way to type anything into it is a keyboard attached
to it. A distribution that cannot be administered remotely is a
distribution for laptops only, and the platform roadmap has never said
that.

It is also the first thing this system will do that *accepts* a
connection. Everything up to here has been outbound: DHCP, `pkg sync`,
`git clone`, an HTTPS fetch. The firewall RFC 0016 built has been
default-drop on input since the day it landed and has never once had
to say no to anything anyone wanted. That changes here, and it is the
reason the design below is shaped the way it is.

## Proposed Design

### A second package, not a bigger one

`build/35-devtools.sh` already builds `sshd`, `sshd-session` and
`sftp-server` — RFC 0019 needed them as the *test peer* for the
client, built and deliberately never installed. Those same three
binaries now also go into a package.

**`openssh-server`, separate from `openssh`.** `pkg install openssh`
has to be able to mean "I want to ssh out of here" without also
meaning "the world may ssh in". One package with a daemon in it cannot
express that, and a machine that starts listening because someone
wanted `scp` is a bad surprise in exactly the category where surprises
are worst.

`sftp-server` is in it because scp has spoken SFTP rather than the old
rcp protocol since OpenSSH 9.0 — without it `scp` *to* this machine
fails, not just `sftp`. `sshd-session` is in it because OpenSSH 9.8
split the daemon and `sshd` alone accepts a connection and dies (RFC
0019 found that the hard way).

**Ed25519 host keys only.** Not a default — the whole of what this
OpenSSH can do. It is built `--without-openssl` (RFC 0019), so there
is no RSA and no ECDSA to generate. Worth saying out loud rather than
leaving someone to find out against an old client.

### The host key is made on the machine, not in the image

`init/services/sshd/run` generates `/etc/ssh/ssh_host_ed25519_key` if
it is not there, on the first start, before it execs anything.

This is the single most important line in the RFC. **A distribution
that ships a host key ships the same key to every machine that
installs it**, which means anybody holding the image can impersonate
any of those machines and read the traffic. It has happened to real
distributions and to a great many appliances, and it is invisible
until somebody looks. Nothing in the Novi image contains a host key;
`novi.iso` has none, no package has one, and the first machine to
start the service makes its own.

`ssh-keygen -A` would have been shorter and would have printed
failures for two key types that cannot exist in this build. Naming the
one that can is clearer than ignoring errors.

### One service, and what "ready" means

`init/services/sshd/` is a longrun in the **base image**, although the
binaries are a package. s6-rc does not check that a run script's
program exists, so a declared-off service pointing at something
not-yet-installed is inert rather than broken — the arrangement
`seatd` and `novi-shell` have had since the base/desktop split (RFC
0007), and it means installing the package is the only step: the
service is already there to turn on.

It declares `notification-fd 3`, and signals **when the host key
exists** — not when a socket is bound. sshd says nothing when it
starts listening, and claiming otherwise would be the "up is not
working" mistake this repo has now made four times (RFC 0014). The
host key is the one precondition anything else can race on:
`ssh-keyscan` against a machine that has not made one yet gets a
refused connection and caches nothing.

`-D` so s6 supervises the listener rather than a daemonised orphan;
`-e` so its output goes to the catch-all log with every other
service's.

### Privilege separation

`sshd:x:22:22` in `/etc/passwd`, group `sshd:x:22:`, locked in
`/etc/shadow`, home `/var/empty`, shell `/bin/false`. `/var/empty`
is created by `03-base.sh` at 0755 root-owned and empty; sshd checks
all three properties at startup and refuses to run otherwise, which is
the point of it.

Both are **base content even though the daemon is a package**, and for
the same reason `/etc/passwd` is repo content rather than a heredoc: a
UID and a directory's mode are baked into the squashed image, so they
are build-time facts. A package that created its own account would be
allocating a UID at install time on a system whose entire file-mode
story depends on them being fixed.

The sandbox is seccomp — `CONFIG_SECCOMP` and `CONFIG_SECCOMP_FILTER`
were already set in `kernel/config-x86_64`, checked rather than
assumed, because the fallback is `rlimit` and the difference is not
visible until a session dies.

### `network.firewall.allow`, and why it is not automatic

The firewall's input chain is default-drop. Something has to let port
22 through. There were two ways to do it and the choice matters more
than the mechanism:

**Rejected: derive the holes from the services.** `services.sshd = on`
could have opened 22 by itself, from a service-to-port table. It is
one key instead of two and it is what most people would expect. It is
also a firewall that opens itself because a daemon started, which is
not a firewall — it is a service registry with a policy file attached.
The whole value of RFC 0016 being *declarative* is that the set of
things reachable from the network is written down in one place a
person chose, not accumulated as a side effect of other decisions.

**Chosen: a second declared key.**

```
network.firewall.allow = 22
network.firewall.allow = 22, 80, 443, 123/udp
network.firewall.allow = none
```

The shipped `/etc/novi/firewall.nft` gains two empty nftables sets and
two rules:

```
	set open_tcp { type inet_service }
	set open_udp { type inet_service }
	...
		tcp dport @open_tcp accept
		udp dport @open_udp accept
```

`novi-state` fills the sets and is the only thing that writes them.
Sets rather than rules in the file because **the holes are
configuration and the file is policy**: a port list belongs in the
same document as the hostname, where `diff` can see it and a
generation can roll it back, while the shape of the filter belongs in
nftables' own format. Empty sets match nothing, so on a machine that
has declared nothing the two rules are the same as not being there.

The cost of the split is that somebody turns on ssh, cannot reach the
machine, and has no idea why. That is a real cost and it gets a real
remedy: it is *not drift* — both keys are exactly as declared, so
`diff` cannot report it and `apply` cannot fix it — so `novi-state`
says it instead, from both commands:

```
warning: services.sshd is on, but the firewall does not allow port 22
warning:     add it:  novi-state set network.firewall.allow 22 && novi-state apply
```

`LISTENING_SERVICES` in `novi-state` is the table behind that
sentence. It exists **only to warn**; nothing in it opens anything,
and a service absent from it is not assumed silent — it is simply not
something the file knows the port of.

Three details in the key that are easy to get wrong:

- **Ports are numbers, never names.** `nft` would resolve `ssh`
  through `/etc/services`, which BusyBox does not ship — so a name
  would work on a build host and fail on the machine, which is the
  worst of the three possible outcomes.
- **Declared and observed are compared canonically.** `22, 80` and
  `80,22` are the same holes, and reporting them as drift would make
  `apply` rewrite the same two ports on every run. Both sides are
  sorted numerically per protocol; when they match, the observer
  echoes the declared string back verbatim so the document's own
  formatting is never "corrected".
- **Firewall off means the key is inert, not drifted.** With no table
  there are no holes to be out of step with, and the observer reports
  the declared value — the same call `network.interface` makes when
  the network service is down. Permanent unfixable drift on a machine
  that simply is not filtering would be a worse answer than silence.

`EARLY_KEYS` gains `network.firewall.allow`, second, after
`network.firewall`: the ruleset reload empties the sets, so filling
them first would fill sets that are about to be replaced. Both
converge before `s6-rc change` runs, so the hole and the wall arrive
together and neither exists for a window without the other.

### Who may log in

`/etc/ssh/sshd_config` is Novi's own file, not the one configure
generates. Three lines differ from upstream and each is there because
of something specific to this system:

**`PermitRootLogin no`.** Not `prohibit-password`. `/etc/shadow` ships
`root::` — no password — which is deliberate for an installable live
image and catastrophic the moment a port is open. `prohibit-password`
would still leave root as the account every scanner on the internet
tries first, one `passwd` away from being reachable. Root logs in at
the console, or someone in `wheel` uses `su`.

**`PasswordAuthentication yes`** with **`PermitEmptyPasswords no`**.
This is the line that looks wrong and is not, and the reason is not
the line — it is what sits behind it.

**A fresh Novi has nobody who can log in.** Not "nobody with a good
password": nobody. root has an empty hash and is refused twice over.
Every other account `novi-state` or `novi-install --user` creates
starts **locked** — `!` in `/etc/shadow`, RFC 0005 — and OpenSSH
refuses a locked account outright. *Including with a key*, which is
the part it is easy to assume is not true: the check in
`allowed_user()` runs before any authentication method is tried. It
was verified rather than assumed, and the first live run of this RFC's
own test was denied by it: an account owning a valid `authorized_keys`,
with `!` in shadow, gets `Permission denied (publickey,password)`.

So opening port 22 on a machine nobody has touched exposes nothing
that can be authenticated to, and the act that changes that is a
person at the console running `passwd`. Turning password auth off
would be marginally stricter and would also mean nobody can ever reach
a machine they did not pre-seed a key onto — not a trade a
general-purpose OS gets to make on its users' behalf.

**There is deliberately no `UsePAM no`.** There is no PAM here
(`--without-pam`), and a build without it does not merely default the
option off — it does not know the keyword, and prints `Unsupported
option UsePAM` on every start and every `sshd -t`. A line whose only
effect is a warning about itself is worse than the absence it was
documenting.

**`LogLevel VERBOSE`**, which records the fingerprint of the key each
session authenticated with — the one line anybody ever wants after the
fact.

Everything else is OpenSSH's default, deliberately. A config that
restates defaults is a config that silently freezes them at whatever
they were the day it was written.

## Alternatives Considered

- **Dropbear.** Smaller, and it would have been a second ssh
  implementation on a system that already has OpenSSH's client built
  and working. Two implementations of one protocol is two sets of
  behaviour to know.
- **sshd in the base image.** It is 1.1 MB and a console base has room
  for it. But a base image that listens by default is a different
  product, and one that ships a listener switched off is a package
  with extra steps.
- **A `services.sshd.port` key.** Moving the port is a real thing
  people do. It also means the firewall key has to follow it, or the
  two disagree — and `network.firewall.allow` already expresses
  "reachable on 2222" exactly. `Port` in `sshd_config` and the number
  in the document is one fact written twice; that is a fair criticism
  and the alternative was worse.
- **Generating the host key in `03-base.sh`.** Discussed above. No.
- **An `authorized_keys` flag on `novi-install`.** Genuinely useful
  and deliberately not here: the installer would be writing a
  credential, and every other credential in this system arrives
  through a tool that owns one file (`passwd`, `novi-wifi`). It is
  roadmap, with a tool, not a flag bolted on.

## Verification

One VM, the real ISO, QEMU user networking with `hostfwd=tcp::2222-:22`,
and a **real OpenSSH client on the host** — off the machine, across the
emulated network, into a Novi whose host key did not exist five minutes
earlier. The sequence is chosen so each step can only pass for one
reason.

| | |
|---|---|
| Firewall up, `allow = none` | `open_tcp` empty |
| `pkg sync` → `pkg install openssh-server` | pulls `zlib`, `openssh`, then the daemon; **`/etc/ssh` has no key** |
| `services.sshd = on` | `up … ready`, key appears, and `apply` warns that port 22 is shut |
| sshd listening | `0.0.0.0:22` and `:::22` — **and the host cannot connect** |
| `network.firewall.allow = 22` | host probe returns `SSH-2.0-OpenSSH_9.9`; `diff` clean |
| `ssh tester@` with a key, account locked | `Permission denied` |
| `chpasswd`, then the same command | `novi` / `uid=1000(tester)` / `Linux 6.10.3-novi` |
| same key in `/root/.ssh/authorized_keys` | `Permission denied` |
| root, password auth, empty password | `Permission denied` |
| `scp tester@…:/etc/os-release` | pulled the file |
| `allow = none` again | host shut out, `s6-svstat` still `up … ready` |

The fourth row is the one that matters most: a daemon bound to
`0.0.0.0:22` that the host cannot reach is the only evidence that the
firewall is doing something, rather than that nothing was listening.

### Three bugs this found, all in the new code

**`exec sshd -D -e` produced `sshd requires execution with an absolute
path`** — once a second, forever, from a binary whose `sshd -t` had
just reported the configuration perfect. sshd re-execs itself for each
connection and refuses to start if `argv[0]` is not absolute. PATH was
never the problem (04-s6.sh puts `/usr/sbin` on it); the bare name
resolved fine and it is `argv[0]` sshd objects to. The run script
spells out `/usr/sbin/sshd`.

**The service declared `notification-fd` and no `timeout-up`.** With
the package not installed, the run script's `exit 1` became a crash
loop and `s6-rc -u change sshd` waited **forever** — `novi-state
apply` hung on it and the console session with it, and boot
convergence would have hung the boot the same way. `network` and
`wifi` are the only other longruns here that declare readiness and
both already bound the wait; this one had simply broken the pattern.
The general rule, now written down: **a longrun that declares
readiness must also declare how long anything waits for it.**

**The `network.firewall.allow` observer read `22 } ` and called it
unparseable.** A `sed` range whose start line also matches the end
pattern does not end on that line — it runs on to the next `}`, which
is the set's own closing brace — and a greedy `.*` then captured to
the last one. `diff` reported permanent drift against a set that was
exactly right, and `apply` rewrote the same port three times and gave
up. `[^}]*` is the fix.

## Impact

- **Base image:** the `sshd` account, `/var/empty`, one s6-rc service
  definition, and two empty nft sets. No binary.
- **Packages:** `openssh-server` (~1.1 MB), depends on `openssh` and
  `zlib`.
- **`novi-state`:** one new key, `network.firewall.allow`.
- **`system.conf`:** `services.sshd = off` and
  `network.firewall.allow = none` are declared, so both are
  discoverable by reading the file rather than the docs.

## Still not done

- **No `Match` blocks, no `AllowUsers`, no per-source rules.** All of
  that is `sshd_config`, which is a real file and stays the
  administrator's.
- **No source-address restriction in the firewall key.** `allow = 22`
  means everyone. A rule scoped to a subnet belongs in
  `firewall.nft`, and saying so is better than inventing a syntax for
  it in a key.
- **No key provisioning at install time**, as above.
- **`sshd` has no `Port` awareness in `LISTENING_SERVICES`** — the
  warning assumes 22, so somebody who moves the port gets a warning
  they should ignore. That is worth fixing when a port key exists and
  not before.
- **Never run on physical hardware**, like everything else here.

# RFC 0021 — WPA3, and the crypto the supplicant already had

**Status:** Implemented
**Depends on:** RFC 0009 (WiFi), RFC 0017 (WiFi in the desktop)
**Corrects:** RFC 0009 § "No WPA3, and this is a stated limitation"

> **Summary.** wpa_supplicant is rebuilt against **wolfSSL** instead of
> its internal crypto, which gives it the elliptic-curve operations
> SAE needs. `novi-wifi add` now writes one network block that is both
> WPA2-PSK and WPA3-SAE, so a machine joins whichever the access point
> offers. Verified against a WPA3-SAE-only AP — `key_mgmt=SAE`,
> `pmf=2`, `sae_group=19` — and against a WPA2-only AP with the same
> block, on `mac80211_hwsim`.

## Motivation & Problem Statement

RFC 0009 shipped WiFi and said, in as many words, that it could not do
WPA3: SAE and OWE call `crypto_ec_*` and the bignum routines beneath
them, `CONFIG_TLS=internal` does not implement any of it, and the build
failed at `undefined reference to crypto_ec_get_prime`. That was true
and it was correctly stated as a limitation rather than left to be
discovered.

Three years of routers later it is not a limitation anyone can live
with quietly. WPA3-Personal is mandatory for Wi-Fi 6E and Wi-Fi 7
certification, which means the 6 GHz band is SAE-only by rule — an
access point may not offer WPA2 there at all. A client that cannot do
SAE does not get a worse connection on those networks; it does not
appear on them. The same is increasingly true of enterprise and campus
networks that have turned transition mode off.

RFC 0009 also named the way in, and named it wrong. RFC 0020 went to
add mbedTLS for HTTPS, looked at wpa_supplicant 2.11 while it was
there, and found the backend does not exist: the tree offers
`openssl`, `gnutls`, `wolfssl`, `internal`, `linux` and `none`, and
`grep -rli mbedtls` over the whole tarball returns nothing. That
correction is written into both RFCs, because a wrong claim repeated
in a roadmap is how the wrong work gets scheduled.

## The argument that had to be made first

The reflex objection is RFC 0006's: this project built `novi-verify`,
a 10 KB static Ed25519 verifier, specifically so that checking a
package signature would not mean linking a TLS library, and RFC 0009
built the supplicant with internal TLS for the same reason. Adding
wolfSSL to the **base image** looks like undoing that in one step.

It is worth being precise about what the rule actually was, because
the precise version permits this and the vague version does not.

**The base image already linked a TLS implementation.**
`CONFIG_TLS=internal` is not "no crypto". It is roughly 200 KB of AES,
SHA-1, SHA-256, RSA, a bignum library and a TLS 1.2 handshake, written
by the wpa_supplicant authors and compiled straight into the binary,
and it has always been there. RFC 0009's rule was *no OpenSSL*. RFC
0006's rule was *verifying a package must not need a TLS stack* —
`novi-verify` is still static, still separate, and still the only
thing on the signature path. Neither rule says the supplicant may not
have crypto; it never did not have crypto.

So the change on the table is swapping one crypto implementation for
another: 200 KB of code with no outside review for 1.4 MB of code that
is FIPS-validated in its commercial form, audited, and maintained by
people whose whole job it is. That is not a widening of the attack
surface so much as a rehousing of it, and the smaller of the two is
the one nobody has looked at.

wolfSSL is dual-licensed GPL-2.0 / commercial. The GPL half is clean
under this project's own GPLv2.

The cost is stated honestly: `libwolfssl.so.43` is 1.4 MB stripped in
the base image, and the base image is where a console-only machine
that never touches WiFi also carries it. That is the same bargain as
`libnl`, which RFC 0009 already made, one order of magnitude up. The
alternative — moving the whole supplicant into a package — is a real
design and is deliberately not this RFC: a laptop with no Ethernet
port cannot install the package that would let it reach the
repository.

## Proposed Design

### wolfSSL, built in the WiFi stage

`build/25-wifi.sh` builds wolfSSL 5.7.6 between libnl and
wpa_supplicant.

Putting it in stage 25 rather than a stage of its own is deliberate.
The rule this repo learned from novi-launcher linking fcft (RFC 0005's
third case) is about a library built in a *later* stage than its
consumer — a backwards dependency that is invisible in every tree
except a clean one. wolfSSL's only consumers are wpa_supplicant and
hostapd, both built in this same stage, so the hazard does not exist.
The day something else links it, it moves.

**Autotools, not cmake, and that is not cosmetic.** wolfSSL's cmake
build has a `WOLFSSL_WPAS` option, and it is not the same set of
defines as autotools' `--enable-wpas`. Built with the cmake flag,
`tls_wolfssl.c` failed on fourteen errors — `SSL_OP_NO_TLSv1`
undeclared, implicit declarations of `wolfSSL_get_client_random`,
`wolfSSL_export_keying_material`, `wolfSSL_get_peer_finished` —
because `--enable-wpas` also turns on `OPENSSL_EXTRA` and about twenty
other defines (`HAVE_SECRET_CALLBACK`, `HAVE_KEYING_MATERIAL`,
`KEEP_PEER_CERT`, `WOLFSSL_DER_LOAD` …) that the cmake option does
not. Reconstructing that list by hand is the mistake; use the switch
upstream maintains.

The price is `autoconf`/`automake`/`libtoolize` on the build host,
because the tarball comes from `git archive` — GitHub's
`/archive/refs/tags/` endpoint is 403 through this environment's proxy
— and carries no generated `configure`.

One `-Wno-error=` is needed and only one. GCC 14 flags
`Hmac_UpdateFinal_CT`'s constant-time trick: it writes into
`hmac->innerHash` as a flat byte array past the union member GCC sized
it from ("writing 16 bytes into a region of size 0 … at offset 816
into destination object 'hmac' of size 784"). That is deliberate in a
routine whose entire point is to touch the same memory regardless of
digest length. Disabling that one diagnostic rather than `-Werror`
wholesale keeps every other warning fatal.

### The supplicant's config

```
CONFIG_TLS=wolfssl
CONFIG_SAE=y          # WPA3-Personal
CONFIG_SAE_PK=y       # SAE Public Key
CONFIG_OWE=y          # opportunistic encryption on open networks
CONFIG_IEEE80211W=y   # management frame protection
```

`CONFIG_IEEE80211W` is not optional dressing: SAE *requires* PMF, and
an AP with `sae_require_mfp=1` refuses to associate without it.

`CONFIG_SAE_PK` binds an SSID to a public key, so a rogue AP with the
same name and the same password cannot impersonate the real one. It
costs nothing once SAE is on.

`CFLAGS`/`LIBS` reach the build by being **appended to the generated
`.config`**, which is a makefile fragment:

```
CFLAGS += -I${ROOTFS}/usr/include
LIBS   += -L${ROOTFS}/usr/lib
LIBS_p += -L${ROOTFS}/usr/lib
```

Passing `CFLAGS=` on the `make` command line instead would *replace*
everything upstream's makefiles put there, not add to it — the same
trap as RFC 0009's exported `LDFLAGS`, one level in.

hostapd, the test peer, gets `CONFIG_TLS=wolfssl CONFIG_SAE=y
CONFIG_IEEE80211W=y` for the same reasons; its default backend is
OpenSSL and it does not ask.

### One network block, both protocols

`novi-wifi add` writes:

```
network={
	ssid="…"
	psk=<32 bytes of PBKDF2, hex>
	key_mgmt=WPA-PSK SAE
	ieee80211w=1
	sae_password="…"
}
```

`key_mgmt` listing both lets the supplicant take whichever the AP
offers, with no second profile and no user-visible choice — which is
the point. `ieee80211w=1` is *optional* PMF: negotiated when the AP
asks, absent when it does not, so the same block still joins a WPA2
AP that has never heard of it.

`sae_password=` is the one uncomfortable line. SAE derives from the
passphrase itself, not from the PBKDF2-derived PSK, so unlike WPA2
there is no way to store a one-way transform and still be able to
authenticate. The plaintext passphrase has to be on disk. This is why
`/etc/novi/wifi.conf` was already 0600 and root-only and why it is not
`system.conf` (RFC 0009: *configuration is declared, secrets are
not*), and it is why the escape hatch exists:

**`novi-wifi add <ssid> --wpa2-only`** writes `psk=` and nothing else
— no `sae_password`, no plaintext anywhere — for anyone who would
rather not have the passphrase recoverable from a stolen disk than be
able to join a WPA3 network. On a machine with RFC 0018 full-disk
encryption the distinction is mostly moot; on one without it, it is
a real choice and belongs to the person, not to us.

## Alternatives Considered

- **A newer hostap tree.** 2.11 is current; there is nothing to move
  to that would have changed this.
- **Backporting the out-of-tree `crypto_mbedtls.c`.** It exists and it
  would have reused RFC 0020's mbedTLS. It is a patch this project
  would then own and rebase forever, against an upstream that does not
  carry it, on the code path that negotiates the key to a network.
  A supported backend beats a maintained patch here by a wide margin.
- **Two network blocks, one WPA2 and one SAE.** Works, and doubles
  every stored credential for no gain — `key_mgmt` already takes a
  list.
- **`ieee80211w=2` (PMF required).** Strictly better against
  downgrade, and it would have made every WPA2 AP unjoinable. `=1` is
  the correct default for a general-purpose OS; a machine that wants
  `=2` can edit the file.
- **Moving wpa_supplicant out of the base image** to avoid carrying
  1.4 MB of wolfSSL. Discussed above: the bootstrap does not work.

## Verification

Two `mac80211_hwsim` radios in one VM, `wlan1` running hostapd from
the test image (built by this stage, never installed), `wlan0` the
station.

**WPA3-SAE-only AP** — `wpa_key_mgmt=SAE`, `ieee80211w=2`,
`sae_require_mfp=1`. Not transition mode: an AP a WPA2-only client
cannot join *at all*, which is what makes it a test of SAE rather than
a test of the fallback.

```
$ printf 'novitest12345\n' | novi-wifi add NOVI_WPA3 --stdin
$ novi-state set network.wifi on && novi-state apply
$ novi-wifi status
ssid=NOVI_WPA3
key_mgmt=SAE
pmf=2
mgmt_group_cipher=BIP
sae_group=19
```

`sae_group=19` is NIST P-256 — the dragonfly exchange ran, on the
elliptic-curve code that did not exist in this binary before.

**WPA2-only AP, same block** — `wpa_key_mgmt=WPA-PSK`, no PMF offered:

```
ssid=NOVI_WPA2
key_mgmt=WPA2-PSK
wpa_state=COMPLETED
```

**`--wpa2-only` stores no passphrase:**

```
$ printf 'hunter2xyz9\n' | novi-wifi add SOMEWHERE_ELSE --wpa2-only --stdin
$ grep -c hunter2xyz9 /etc/novi/wifi.conf
0
```

### A bug worth recording

The first live run failed with `novi-wifi status` reporting *"the
supplicant is not running"*. The cause was three lines away from the
message: `wpa_passphrase`'s output ends with a closing `}`, and the
SAE keys were being appended **after** it, putting `key_mgmt`,
`ieee80211w` and `sae_password` at file scope. wpa_supplicant refused
to parse the file and the service never came up.

A message about a *service* produced by a syntax error in a *config
file* is the same shape as three earlier bugs in this repo — the
report and the fault are in different subsystems. The fix drops the
brace, appends, and puts it back, and refuses to edit the output at
all if the last line is not `}` rather than corrupting it blind.

## Impact

- **Base image:** +1.4 MB (`libwolfssl.so.43`). wpa_supplicant itself
  is 1.05 MB, slightly smaller than the internal-TLS build.
- **`novi-state`:** no new keys. `network.wifi` is unchanged; which
  protocol a network uses is a property of the network, not a thing to
  declare.
- **RFC 0009 and RFC 0020** are amended where they say WPA3 is not
  possible and where they name mbedTLS as the way to it.

## Still not done

- **OWE is compiled in and untested.** It needs an open AP running
  `wpa_key_mgmt=OWE`, and `novi-wifi` has no verb for joining an open
  network at all yet.
- **SAE-PK is compiled in and untested**, and untestable without an AP
  provisioned with a key pair.
- **WPA3-Enterprise (192-bit)** needs certificates and an EAP method;
  none of that is here.
- **None of this has run on physical hardware.** Every radio in every
  test is `mac80211_hwsim`.
